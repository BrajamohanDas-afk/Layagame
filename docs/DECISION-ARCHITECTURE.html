01Why

The current build asks Laya a classifier question: "here is the whole 28×31 maze as ASCII, you are at a junction, which direction feels best?" The model has no state, no objective, no memory and no consequence model — loops, a left-leaning prior and ignoring distant food are expected outcomes, not bugs in the checkpoint.

Observed symptoms (live runs, 2026-10-06):

  • Junction loops — the same junction revisited 2–3× before anything changes (A → P → B → P → A → …).
  • Directional bias — with legal moves: left, right, left wins far too often; this looks like a prior/label bias, not maze reasoning.
  • No food awareness — Pac-Man kept circling cleared ground with pellets elsewhere; the current 30-move no-pellet net is too late and only reshuffles directions.
  • Fresh every junction — no memory of where it just came from or what it tried.

The fix is not a longer prompt. The fix is a richer game state and a smarter decision pipeline around Laya, while keeping the actual model prompt small.

Current code folds in: safe_choice → safety controller, stuck_retry + pellet_distance → exploration controller, chase_move → chase controller. Junction-only decisions and the in-process CUDA requirement from PLAN.html stay untouched.

03Feature extractor

The game engine owns all pathfinding and spatial calculations. It computes exact distances, reachable pellet counts, zones, danger distances, exploration coverage, and route-level information using the maze graph / BFS. Laya never performs pathfinding, geometry, distance calculation, or maze-traversal reasoning from ASCII; Laya only evaluates the engine-provided features and chooses the strategic direction.

Feature (per legal move)Meaning / source
pelletBFS distance from that neighbour to the nearest remaining pellet (Game.pellet_distance() exists)
zonecount of remaining pellets within a BFS radius (e.g. 12) of that neighbour — "is this a rich direction?"
powerBFS distance to the nearest power pellet
dangerlow / med / high from the nearest deadly ghost: its distance and whether that move decreases the distance to it
edibledistance to the nearest frightened ghost (chase opportunity), - if none
newexploration score: fraction of tiles reachable within a radius that were not visited since the last pellet
seenthe move was taken from this junction within the last K decisions (loop penalty input)

04Memory & loop detection

  • Junction memory — ring buffer of the last 5–10 decisions: junction id (x,y), entered-from, chosen move, tick. No full history in the prompt; a one-line summary only.
  • Visit counts — rolling count per junction (decay over ~50 decisions) for the seen feature and the prompt line.
  • Junction-cycle detector — periodic pattern in the junction sequence (e.g. A B A B, A B C A B C).
  • State-repetition detector — same (tile, direction) recurring within the window.
  • Reward stagnation — the existing no-pellet counter, now a fallback rather than the only trigger.

When a loop is detected the exploration controller: forbids the branch that closed the loop, allows a reversal, and prefers the least-visited / most-unexplored neighbour.

05Controllers & aggregator

#ConditionControllerDeterministic rule
1deadly ghost within 2 tiles and closingsafetymax clearance move (extends today's safe_choice); may reverse
2loop detector firedexplorationforbid closing branch, allow reversal, prefer unexplored (today's pellet-seeking becomes the fallback)
3frightened ghost nearby and no deadly ghost adjacentchasemove that decreases distance to the edible ghost
4otherwiseLayamodel probabilities + engine scores:
final_score(move) = 1.0 · model_prob
                  + 0.25 · pellet_score      (closer to food is better)
                  + 0.15 · explore_score     (unexplored is better)
                  - 0.25 · loop_penalty      (recently seen branch)
                  - 0.40 · danger_penalty    (toward deadly ghosts)
argmax(final_score) -> move

Starting weights only — WP4 tunes them against the metrics. Every move is logged with its source: laya | danger | loop | chase.

06Laya presentation (anti-bias)

  • Randomised option order with explicit mapping — present A = right, B = left, C = up etc. in a shuffled order; translate the chosen key back to a direction. Tests whether "always left" is a position/order bias.
  • Neutral labels variant — option A / B / C with the mapping known only to the engine; removes directional semantics entirely. Decision by measurement (user decision 2026-10-06).
  • Cache-safe shuffling — the shuffle is seeded by a hash of the state, so identical states always present identical options and the (state, legal) cache stays valid.
  • Keep all guards: truncation, collapsed options, probs sum ≈ 1.

07Prompt budget

Hard constraint: the state once hit truncated at 407 tokens (budget ≈ 397). The full 28×31 board alone is ~350 tokens — there is no room for features, objective and memory on top of it.
  • Decision (user, 2026-10-06): drop the full board; send features only. Do not raise max_len.
  • The engine now owns all pathfinding and spatial calculations; Laya owns strategy ("which direction is better").
  • Keep the usage["truncated"] / collapsed-options guards; they must stay silent in every run.
